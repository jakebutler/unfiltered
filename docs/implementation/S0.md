# S0 — clinical persistence and access qualification

October 9, 2026. This is a local technical qualification milestone. It does not complete the patient interface, clinical workflow, hosted deployment, voice, research, or AWS package.

## Implementation

`packages/clinical-core` provides bounded source-linked confirmations, separate intake completeness and delivery, native FHIR handoff/receipt reconciliation, role-specific work authority, and a strict DigitalOcean adapter. `scripts/qualification` exercises the persistence boundary. `infra/local` starts a pinned synthetic Medplum stack and tests named-user access using genuine OAuth/PKCE identities.

The local server runs Medplum `5.2.3-39c4978` with PostgreSQL and Redis, loopback-only app/API ports, private generated credentials, and a non-root writable binary volume. The isolated Colima profile leaves the user's preexisting Docker context untouched.

The core report explicitly leaves named authorization unqualified; the separate access harness supplies that local evidence. Neither result qualifies the eventual application API, CareTeam-to-policy synchronization, staff transition attribution, or hosted Medplum plan.

## Findings and corrections

Independent review found and verified corrections for premature transaction qualification, stale review digests, and aggregate source size exceeding the receipt reader. Root review corrected inherited numerical clarification caps, complete-intake labels without trusted sufficient-detail evidence, and medical disposition authority being implied by broad clinical read visibility.

The first actual server run (`e4b10ed0-d0d9-42fd-9a50-343dd1baecf4`) failed qualification truthfully: this server accepted an intentionally malformed Task. The probe now uses a stale `If-Match` update, proving a real execution-level failure in both batch and transaction. Batch preserves its valid sibling; the equivalent transaction rolls it back. A positive valid transaction is also required. Application validation remains essential; do not rely on this server's default schema rejection.

Actual Binary upload exposed a volume permission problem despite healthy API checks. A minimal network-disabled initialization container sets storage ownership for UID 1000; the server remains non-root.

## Measured access limitation

A copied native signed `/storage` URL still returned the exact source after role downgrade. Canonical FHIR QuestionnaireResponse, DocumentReference and Binary reads with the same downgraded token were denied. The application must retain staff FHIR tokens server-side, resolve sources through freshly authorized canonical reads, and not emit native reusable signed URLs. Each Binary must have an access-controlled `securityContext` and each source DocumentReference the appropriate patient subject. Application enforcement is still to implement and test.

## Reproduce

Follow [local setup](../../infra/local/README.md), then run:

```sh
npm run foundation:build
npm run foundation:test
node infra/local/qualify-access.mjs --write-runtime-env
node infra/local/qualify-core.mjs --allow-synthetic-writes
```

The access script refuses to overwrite existing private runtime credentials. Once they exist, omit `--write-runtime-env` for a fresh isolated authorization run. Core receipts remain in ignored private `*.receipt.json` files and retain synthetic identifiers for inspection. Do not remove fixture data as a substitute for resolving uncertain receipts.
